# Ko-sign 白皮書 — 運作原理與機制

> 本文描述 Ko-sign 的**協定設計與運作機制**(它「為什麼這樣設計、靠什麼保證安全」),
> 不是程式碼說明。目的是讓讀者確認整體方向與信任模型是否正確。
> 版本:草稿 v0.1 · 網路:Kaspa testnet-10 (Toccata)

---

## 1. 摘要

Ko-sign 是一個**由 Kaspa L1 直接強制執行的多簽金庫**(M-of-N multisig treasury)。
資金的移動規則——「需要 N 位擁有者中的 M 位核可才能轉出、只能轉給提案指定的對象與金額」
——不是由某個伺服器或鏈下服務把關,而是**寫進鏈上的 covenant(契約)**,由共識層強制。

與「帳戶模型」的智能合約多簽不同,Kaspa 沒有全域可變狀態的帳戶;Ko-sign 把多簽的
**提案狀態直接編碼在 UTXO 的 covenant 內**,每一次提案、每一次核可、每一次執行,
都是一筆**已確認的鏈上交易**。沒有「鏈下暫存等湊簽名」這回事。

---

## 2. 背景:Kaspa、UTXO 與 Toccata covenant

- **UTXO 模型**:Kaspa 沒有合約帳戶與可變儲存。價值以 UTXO(未花費輸出)存在,
  交易消耗舊 UTXO、產生新 UTXO。
- **Toccata 硬分叉**為 Kaspa 帶來 **L1 covenant**:一個 UTXO 可以附帶「花費條件」,
  並且能對「花用它的那筆交易」做**內省(introspection)**——檢查該交易的輸入、輸出、
  金額、腳本、時間等。這讓 UTXO 能強制「我只能被花在符合某些規則的交易裡」。
- **Covenant 譜系(covenant id)**:Toccata 讓一組 UTXO 共享一個由共識層計算、
  無法偽造的 32-byte 身分。延續性輸出會**繼承**授權它的輸入的 covenant id。

Ko-sign 完全建立在這三項之上。下面用到的所有「保證」,最終都歸結為:
**共識層在驗證每一筆交易時,會重新執行 covenant 的內省規則,不符合就拒絕入塊。**

---

## 3. 設計目標與信任模型

**設計目標**

1. **L1 強制**:能不能動資金,由鏈上規則決定,不依賴任何中心化服務的誠實。
2. **真・多方**:每位擁有者用自己的金鑰核可;沒有任何一方代持他人金鑰。
3. **資金不可被鎖死**:即使所有鏈下輔助資料遺失,只要金鑰與成員設定還在,
   資金永遠取得回。
4. **可重建**:整個狀態能單純從鏈上重建。

**信任模型(誰被信任什麼)**

| 角色 | 被信任做什麼 | 不被信任 |
|---|---|---|
| Kaspa 共識層 | 強制 covenant 的所有規則(門檻、收款人、金額、譜系、時間) | — |
| 擁有者金鑰(M-of-N) | 唯一能授權「提案 / 核可」的權柄 | 單一擁有者無法越過門檻動用資金 |
| 任何輔助服務 / UI / 索引器 | **不被信任**——只是組交易、顯示狀態的便利層 | 不能繞過鏈上規則,弄壞了也不會損失資金 |

關鍵原則:**權柄是金鑰,真相是鏈。** 其餘一切都是可重建的鏡像。

---

## 4. 核心概念:treasury 的譜系身分(treasuryId)

每一個 treasury 在「創世(genesis)」時誕生一個 **treasuryId**,它就是 Kaspa 共識層計算出的
**covenant id**:由創世交易的「資金來源 outpoint + 產出的輸出」決定性地雜湊而來。

- treasuryId **不可偽造、不可重用**:任何人都無法另外造出宣稱屬於同一 treasury 的 UTXO。
- 屬於同一 treasury 的所有 UTXO(下面的 KoRoot / KoVault / KoProposal)都帶**同一個
  treasuryId**,並在每次延續時由共識層強制繼承。
- 這讓「哪些錢、哪些提案屬於這個 treasury」由協定層回答,而不是靠地址或標籤。

> 為什麼需要它:在 UTXO 模型裡,相同「成員 + 門檻」的兩個 treasury 可能算出相同的 P2SH
> 地址。treasuryId 在協定層把它們**徹底區分**,確保操作永遠針對正確的 treasury。

---

## 5. 三種 covenant 物件及其角色

一個 treasury 由三類 covenant UTXO 組成,各司其職:

### 5.1 KoRoot — 提案工廠 / 治理錨點
- 持有 treasury 的**成員清單(公鑰)與門檻 M**,這些是**不可變**的身分前綴。
- 內含一個 **proposalNonce**(提案序號),每產生一筆提案 +1,保證提案編號唯一、不重放。
- 作用:**只能被花在「合法地產生一筆新提案」的交易裡**——它一邊延續自己(nonce+1),
  一邊鑄出一個帶正確初始狀態的 KoProposal。

### 5.2 KoProposal — 單筆提案的狀態機
承載一筆提案的完整狀態(編碼在它的 covenant 內):
- 提案編號、操作類型(目前為「轉出 KAS」)、**收款人**、**金額**、手續費上限
- **到期時間 expiresAt**、**執行延遲 executionDelay**(時間鎖欄位)
- **approvalBitmap(誰已核可)**、**approvalCount**、**status(待決 / 已核可 / 已取消 / 已執行)**

它的花費規則強制了狀態機:核可只能「翻開自己對應的那個 bit、計數 +1」,
達到門檻時 status 變為「已核可」;到期後可被關閉。

### 5.3 KoVault — 金庫(主資金)
- **無狀態(stateless)**:它的花費腳本只由「成員 + 門檻 + 提案模板」決定,因此
  **地址固定不變**——可以印在收款頁上、長期重複使用。
- **只能被花在「執行一筆已核可提案」的交易裡**:該交易必須同時帶上對應的、已達門檻的
  KoProposal,並且付給提案指定的收款人、指定金額,找零退回同一個金庫地址。

## 6. 狀態與「模板」機制

提案的可變狀態(核可情況、計數、狀態)存在 covenant 內一個**固定寬度的狀態區**;
成員與門檻則在**不可變的前綴**。這帶來一個關鍵性質:

- **模板雜湊不變性**:把「前綴 + 後綴」(扣掉中間會變動的狀態區)雜湊起來,得到一個
  **與 treasuryId、與當下狀態都無關**的模板雜湊。
- 因此 **KoVault 可以「釘住」一個模板**,意思是:「我只接受『任何一筆屬於本 treasury、
  形狀符合此模板、且已達門檻』的提案來授權我」——而不需要預先知道每一筆提案長什麼樣。
- 這也解開了一個雞生蛋問題:模板獨立於 treasuryId,讓創世能先算模板、再由共識層賦予 treasuryId。

> 直觀理解:成員/門檻是「身分」,寫死在腳本骨架;核可進度是「狀態」,只動中間那塊。
> 金庫驗的是「骨架對不對 + 進度夠不夠」,不在乎細節長相。

## 7. 生命週期

```
        (資金來源 UTXO)
              │  genesis:一筆交易產生 KoRoot + KoVault,
              ▼  共識層由此推導出 treasuryId
   ┌──────────────────┐        ┌──────────────────┐
   │     KoRoot     │        │    KoVault     │  ←─ 固定地址,可持續收款
   │  成員/門檻/nonce  │        │   (無狀態金庫)    │
   └────────┬─────────┘        └─────────┬────────┘
            │ propose:花 KoRoot,                │
            │ 鑄出一筆 KoProposal,nonce+1        │
            ▼                                      │
   ┌──────────────────┐                           │
   │   KoProposal   │  approve × M:每位擁有者    │
   │  收款人/金額/bitmap│  各送一筆鏈上交易,翻 bit   │
   │  /count/status    │  達門檻 → status=已核可     │
   └────────┬─────────┘                           │
            │           execute:同時花 KoProposal │
            └──────────────┬───────────────────────┘
                           ▼
              付款給收款人 + 找零退回固定金庫地址
```

各步驟要點:

- **創世(genesis)**:用一筆一般資金 UTXO,在同一筆交易裡產生 KoRoot 與 KoVault。
  付這筆款的人**不需要是擁有者**——創世出資與成員身分是獨立的;成員身分是「把哪些公鑰
  寫進 covenant」。
- **提案(propose)**:由一位擁有者發起並簽名(視為第一個核可)。KoRoot nonce 前進,
  確保提案不可重放。
- **核可(approve)**:每位擁有者用自己的金鑰**各自送一筆鏈上交易**,covenant 驗證簽名
  屬於某位成員、且尚未重複核可,然後翻開對應的 bit。達到 M 即「已核可」。
- **執行(execute)**:由**一位擁有者簽名觸發**(沿用核可的用戶端簽名模型)。授權的核心
  仍是「鏈上那筆已達門檻的提案狀態」,但額外要求觸發者證明自己是成員之一——確保只有
  擁有者能決定資金**實際送出的時點**。covenant 同時嚴格要求「只能付給提案指定的收款人與
  金額,找零回金庫」,所以去向無法被任何人竄改。
- **入金 / 掃入(deposit / sweep)**:金庫地址固定,任何人可直接轉入。直接轉入的款項
  會先以「未納管」UTXO 停在該地址;一個**無權限的掃入規則**可把它們併入受 covenant
  控制的金庫輸出。掃入規則只允許「把錢掃進來」(輸出 ≥ 輸入 − 手續費),**不可能掃走**。
- **到期(expiry)**:提案帶到期時間;逾期未執行的提案可被關閉,釋放其押金,之後重新提案。

### 7.1 並行與排序模型

每一筆提案是**獨立的 KoProposal UTXO**,彼此不相干。因此 Ko-sign **支援多筆提案同時
存在、同時被各自核可**——Queue 裡可以有很多筆已核可、等待執行的提案。

UTXO 模型只在兩個動作上產生天然的**串行化(排序)**,但都不妨礙「多筆並存」:

| 動作 | 經過的單一 UTXO | 效果 |
|---|---|---|
| **建立提案** | KoRoot(單一 UTXO,每次 nonce+1) | 同瞬間兩人發提案會競爭同一個 KoRoot,一個成功、另一個對新的 KoRoot 重試;nonce 確保編號唯一且不可重放 |
| **執行** | KoVault(單一金庫 UTXO) | 兩筆執行不能花用同一個金庫 UTXO;執行一筆會產生**新的**金庫 UTXO,下一筆對新的金庫執行即可 |

換言之:**並行的是「提案 + 核可」;串行的只是「建立」與「執行」這兩個會碰到單一 UTXO 的
時點**——而那只是先後順序,不是「必須把前一筆整個走完」。

**實例(2-of-3,金庫 100 KAS,要同時付 Alice 30、Bob 20):**

```
① Carol 建立提案#1(付 Alice 30):花 KoRoot(nonce0)→ KoRoot(nonce1)+ 提案#1   [#1 1/2]
② Carol 建立提案#2(付 Bob 20) :花 KoRoot(nonce1)→ KoRoot(nonce2)+ 提案#2   [#2 1/2]
   ↑ 建立一筆接一筆(都動 KoRoot),但兩筆提案現在「同時存在」為獨立 UTXO

   Queue:  [ 提案#1 Alice 30  1/2 ]   [ 提案#2 Bob 20  1/2 ]

③ Tony 核可 #1 → 2/2 已核可        ④ Pete 核可 #2 → 2/2 已核可
   (各自一筆交易,順序/同時皆可,互不相干 ← 這就是「並行」)

⑤ 某 owner 執行 #1:花 金庫(100)+ 提案#1 → 付 Alice 30,產生新金庫(70)
⑥ 某 owner 執行 #2:花 金庫(70) + 提案#2 → 付 Bob 20, 產生新金庫(50)
   ↑ #2 用的是 #1 執行後的「新金庫 UTXO」;執行順序不綁編號,先被核可的先執行
```

注意:**核可不檢查餘額,執行才檢查**。若金庫 100、#1 要 80、#2 要 50,兩筆都能被建立與
核可;但 #1 先執行後金庫剩 20,#2 執行時因 < 50 會失敗,直到金庫被補足。核可表達意願,
實際資金約束由 covenant 在執行當下強制。

## 8. 授權與安全性質(L1 強制了什麼)

對每一筆嘗試動用 treasury 的交易,共識層重新執行 covenant 規則,以下任一不滿足即**拒絕**:

1. **譜系**:被花的 UTXO 與產出的延續輸出必須帶正確的 treasuryId(不可跨 treasury 盜用)。
2. **成員與門檻**:核可的簽名必須來自被寫死的某位成員公鑰;執行前 approvalCount ≥ M;
   **執行本身也必須由一位成員簽名**(只有擁有者能觸發資金送出)。
3. **去向約束**:執行時付款的**收款人與金額**必須等於提案狀態所記載者;找零必須回金庫。
4. **狀態單調性**:核可只能加一個尚未設定的 bit;狀態只能依規則前進(待決→已核可→已執行)。
5. **不可重放**:proposalNonce 單調遞增,舊提案無法被重用。
6. **時間**:到期 / 執行延遲等時間欄位由鏈上時間檢查。

**這些都不依賴任何鏈下元件的誠實。** 鏈下服務即使被攻破,也只能組出「不合規則因而被
共識層拒絕」的交易,無法讓資金違規離開金庫。

## 9. 資金安全性質(為什麼鎖不死)

- **金庫永遠可動**:金庫無狀態,其腳本只由「成員 + 門檻 + 模板」決定,可**決定性重建**。
  只要 M 位擁有者持有金鑰、且知道成員清單與門檻,就永遠能組出合法的提案→核可→執行。
- **KoRoot 可尋回**:其唯一變動量 proposalNonce 是小整數,可**枚舉**比對鏈上 UTXO 找回。
- **提案參數可從鏈上取得**:發起提案的那筆交易已把收款人、金額、時間等參數揭露在鏈上,
  因此任何一筆提案都能從鏈上歷史完整重建。
- **直接轉入不會卡死**:固定金庫地址 + 無權限掃入,確保「別人直接轉錢進來」的款項
  總能被併入並動用,且掃入過程無法偷走。

**真正不可遺失的只有「擁有者私鑰」與「成員清單 + 門檻 + 合約版本」。**
其餘鏈下資料都是可重建的鏡像。

## 10. 可重建性與索引器(indexer)

Ko-sign 的狀態真相在鏈上,輔助資料只是鏡像。一個**唯讀索引器**可以:

- 掃描帶有某 treasuryId 的 covenant UTXO 與相關交易,
- 重建目前的提案狀態、核可進度,與完整歷史(Queue / History),
- 完全不依賴任何單一機器的本地檔案。

索引器屬於**穩健性與去中心化**的升級(換機可還原、多方狀態一致),
而**非安全性的必要條件**——沒有它資金也鎖不死。這是後續工作項目。

## 11. 與「帳戶模型」多簽的差異

| 面向 | 帳戶模型多簽 | Ko-sign(UTXO + covenant) |
|---|---|---|
| 提案儲存 | 常見作法:鏈下收集簽名,湊夠才上鏈 | **提案與每次核可都是鏈上交易** |
| 狀態真相 | 合約儲存 / 後端 | UTXO 的 covenant 狀態 |
| 地址 | 單一帳戶地址 | 金庫地址固定;提案是另立的短命 UTXO |
| 執行授權 | 合約檢查 | covenant 內省 + 已核可狀態,執行無需簽名 |

(本文刻意不與特定產品比較;上表僅就模型差異說明。)

## 12. 已知限制與未來工作

- **共用地址(無 per-treasury salt)**:成員與門檻完全相同的兩個 treasury 會共用金庫地址;
  treasuryId 在協定層仍能區分、掃入也無法盜走,但「直接轉入」可能被歸到相同成員的姊妹 treasury
  (錢仍在相同成員掌控下,不會遺失)。加入每個 treasury 專屬的 salt 可讓地址唯一。
- **並行提案(實作層)**:協定層已支援多筆同時存在的提案(各自獨立 UTXO,見 §7.1);
  目前**工具/前端僅追蹤單筆**,屬待補的實作層功能,而非 UTXO 或協定的限制。建立會經
  KoRoot 排序、執行會經金庫排序(兩者皆只是先後順序)。
- **鏈下鏡像同步**:目前輔助資料是本地鏡像,跨機器/多方可能不同步;索引器可解。
- **時間鎖語意**:到期 / 執行延遲的邊界情形仍在打磨(細節見 `docs/RISKS.md`)。
- **操作型別**:目前提案僅支援「轉出 KAS」;機制可延伸到其他受約束的操作。
- **金鑰簽名工具化**:擁有者以自有金鑰於用戶端簽名(避免任何一方代持金鑰);
  分散式簽名交換與更友善的簽名器是進行中的工作。

---

## 13. 結語

Ko-sign 把多簽金庫的「規則」從「相信某個服務」下沉到「相信 Kaspa 共識層」:
**權柄是金鑰,真相是鏈,其餘皆可重建。** 只要這條原則成立,方向就是對的——
其上的 UI、索引器、簽名器,都是讓它更好用、更去中心化的外圍,而非安全性的前提。
