whitepaper · v1

Multisig, enforced by Kaspa L1

Ko-sign is an M-of-N treasury whose rules are not a promise made by software — they are consensus rules. Every proposal, approval, rejection and execution is a covenant transaction validated by every Kaspa node.

status experimental · live on testnet-10 · stack Toccata · Silverscript · KIP-10 · KIP-20

1 · Abstract

Multisignature custody normally lives in one of two places: a smart-contract account on an account-based chain, or an off-chain signature-collection ritual around a P2SH script. Ko-sign takes a third path made possible by Kaspa's Toccata upgrade: the multisig itself is a set of interlinked UTXO covenants. The M-of-N policy, the proposal queue, the per-owner approval bitmaps and the payout rules are all state carried by on-chain outputs, and the only way that state can move is along transitions the script — and therefore the network — permits. The reference client is a pure browser application: it builds covenant transactions in WebAssembly, signs them locally with BIP340 Schnorr, and submits them directly to a public Kaspa node over JSON wRPC. There is no backend, no custodian, no admin key.

2 · Why covenants, not signatures

A classical multisig script says: “M of N signatures can spend.” Everything else — what is being approved, who has signed so far, whether an approval was reused — lives off-chain and must be trusted. A covenant flips this: the output itself constrains the transaction that spends it. With Kaspa's KIP-10 transaction introspection a script can read the spending transaction's outputs, and with KIP-20 a network-enforced 32-byte covenant id ties a family of outputs to a common genesis. Ko-sign uses both to guarantee:

  • the vault can only be spent together with an Approved proposal of the same covenant lineage;
  • a proposal can only advance by one legal step at a time — sign, reject, execute, or expire;
  • each owner's approval is recorded in an on-chain bitmap, so approvals cannot be duplicated or replayed;
  • the payout must match the proposal — recipient, amount and fee ceiling are enforced by script.

3 · Architecture

A treasury is three covenant scripts sharing one covenant id, minted together by a single genesis transaction:

        genesis tx  ──┬── output 0 → KoRoot   (policy + nonce + owner set)
                      ├── output 1 → KoVault  (the vault that holds funds)
                      └── output 2 → change

  KoRoot   carries state: nonce · threshold · ownerCount · owners[5]
             spending it = creating a proposal, or applying a signer change
  KoVault  holds funds at a FIXED address; spendable only alongside an
             Approved KoProposal of the same covenant id
  KoProposal one per proposal: operation, recipient hash, amount,
             max fee, expiry, approval/reject bitmaps, status

State encoding. Root state is a compact push sequence — enc(nonce) · enc(threshold) · enc(ownerCount) · 5 × enc32(owner) — with unused owner slots padded by a NUMS point (a public key with no known private key, so padding can never sign). Because owners and threshold are state, not part of the address, the signer set can change while the vault address stays fixed.

Unique addresses. Each treasury embeds a random 32-byte salt in the vault script, so two treasuries with identical owner sets still get distinct deposit addresses. The root and proposal scripts are salt-agnostic; clients disambiguate by covenant id and by walking outpoints from the genesis transaction.

4 · Proposal lifecycle

  propose   owner spends KoRoot → new Root (nonce+1) + Proposal P₀
            witness: proposer, sig, operation, recipient-hash, amount,
                     maxFee, expiresAt, executionDelay
            the proposer funds the proposal bond from their own wallet
  approve   owner spends Pᵢ → Pᵢ₊₁ with their bit set, count+1
  reject    owner spends Pᵢ → Pᵢ₊₁ with a reject bit; once approval can
            no longer reach M, status becomes Failed
  execute   count ≥ M: ANY owner spends Vault + Proposal together;
            the covenant forces an output paying exactly the proposed
            amount to the proposed recipient, and a vault continuation
  close     past expiry, the proposal can be closed and the bond reclaimed

Status is a pure function of the bitmaps: Pending → Approved when count ≥ M, Pending → Failed when N − rejects < M. Every transition is one transaction, so the full audit log — who signed what and when — is reconstructible from the DAG alone.

Signer changes at a stable address

Changing owners or threshold is operation 2: a config proposal commits to the new set via a hash (config_commit(threshold, count, owners)) published in the proposal, and the human-readable set travels in the transaction payload for other clients to verify against that commitment. Once approved, applying it spends the KoRoot and installs the new owner state in the continuation — same covenant id, same vault address, new policy.

5 · On-chain recovery

The genesis transaction carries a compact KOSGN inscription in its payload:

"KOSGN" · version · threshold · ownerCount · salt[32] · owners[32 × n]

Given nothing but a vault address, any client can find the genesis via a public indexer, decode the inscription, rebuild all three covenant scripts, and locate the live KoRoot by walking its spend history from genesis — picking up every signer change on the way. A treasury is therefore recoverable from the chain alone: no server, no database, no backup file.

6 · Client architecture — zero backend

  browser ──(wasm)── builds covenant txs          tools/wasm-tx (Rust → WASM)
          ──(BIP340)─ signs sighashes locally      key never leaves the tab
          ──(JSON wRPC)─ submits straight to a     public node picked via
                         Kaspa node                kaspa-resolver, or your own
          ──(REST indexer)─ rebuilds queue,        api.kaspa.org / api-tn10
                         history & audit logs      localStorage = cache only

Everything the UI shows — balances, the proposal queue, per-proposal audit logs, signer activity — is derived from chain data. Local storage is a cache; deleting it loses nothing. The same property gives multi-device consistency for free: a co-signer on a cold machine opens the vault URL and the client reconstructs the treasury from the DAG.

7 · Security model

propertyenforced by
funds move only via Approved proposalcovenant script + Kaspa consensus
approval uniqueness / no replayon-chain bitmaps in proposal state
proposal ↔ vault bindingKIP-20 covenant id (network-enforced)
payout correctness (recipient, amount, fee cap)KIP-10 introspection in the execute path
sweep value preservation (no fee-burn griefing)the deposit path requires the consolidated output to keep every sompi of the vault inputs — the sweeper funds the network fee
key custodyyour browser — raw keys sign locally and are never transmitted
data availabilitythe Kaspa DAG itself (+ any public indexer)

The client is untrusted infrastructure: a malicious frontend or node can censor or lie about state, but cannot move funds — no set of transactions it could craft will validate without M legitimate owner signatures over the covenant's sighashes. The main residual risks are those of any key-based system (owner key compromise up to M−1 is tolerated by design) and the usual caveats of experimental script primitives on a testnet.

8 · Wallet connectivity

Two connection modes exist today. A manual raw key is the full covenant signer — it can propose, approve, reject and execute. KasWare connects as an owner identity and can deposit into the vault (sendKaspa) and display balances, but its signPskt API only signs inputs of the wallet's own addresses, so it cannot yet sign covenant P2SH inputs — the client states this limitation explicitly. Hardware wallets and further extensions are future work.

9 · Limitations & roadmap

  • Testnet-first. Covenants ship with Kaspa's Toccata line; Ko-sign runs live on testnet-10 and follows the upgrade path toward mainnet.
  • Compiler in the browser. Covenant scripts are compiled ahead of time; moving the Silverscript compiler itself to WASM removes the last build-time dependency.
  • Wallet signing. Covenant-aware signing in extension/hardware wallets (raw-sighash or covenant-aware PSKT) would retire the manual-key requirement.
  • Formal verification of the three scripts, and third-party audit, are open items before any mainnet deployment with real value.

10 · Conclusion

Ko-sign demonstrates that a serious custody primitive — proposal-based M-of-N treasury management with mutable signer sets, on-chain audit logs and chain-only recovery — can be built on a pure UTXO BlockDAG with nothing but script, and operated with nothing but a browser. The policy is not in a database and not in a contract account balance: it is in the outputs, where every Kaspa node checks it, block by block, in seconds.

⚠ experimental software. Ko-sign is research-grade and currently deployed on Kaspa testnet-10. Do not use it to custody meaningful value until the underlying network upgrade and the scripts themselves have been audited and reach mainnet.
